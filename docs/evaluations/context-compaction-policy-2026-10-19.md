# Eidos 压缩触发与 Codex 对照 · 2026-10-19

这次 Run 的问题有直接证据。Eidos 把 200,000 Token 窗口中的 128,000 Token 预留给输出，所以输入预算只有 68,000。压缩器又排除最近三步，只处理更早的历史。系统没有给完整请求设置压缩后的目标大小。系统因此会反复提交小摘要，并再次发现输入超过预算。

## 这次为什么压缩了 14 次

### 1. 输入预算在窗口的 34% 处就耗尽

Run 冻结配置如下：

```text
上下文窗口 W       = 200,000
每次请求最大输出 R = 128,000
安全余量 M         =   4,000
可用输入预算 B     = W - R - M = 68,000
```

[`budget.py`](../../runtime/eidos_runtime/context/budget.py) 使用完整的 `request_max_output_tokens` 计算预留。窗口压力分支在输入投影超过 B 时触发。它不等待界面圆环达到 80%。

这个预算并非算术错误。若请求确实需要允许 128K 输出，系统必须为它留出空间。产品的问题在于：当前配置同时承担模型输出上限和日常请求输出预算两个职责。较大的最大输出会显著提前输入压缩。界面只展示以 W 为分母的上下文占用，也没有解释较小的 B。

### 2. 最近三步被排除，大块内容暂时不能压缩

[`ContextRepository`](../../runtime/eidos_runtime/db/repositories/context.py) 固定设置 `RECENT_CONTEXT_STEPS = 3`。仓库先把最近三步归入受保护集合，再把这个集合排除在旧历史候选之外。窗口压力分支也使用这套候选。

这次前四份摘要新增覆盖的步骤和缩减如下。时间均为北京时间。Token 是输入投影，不能当作前后成对的 Provider 实测值。

| 压缩发生位置 | 新纳入摘要的步骤 | 输入投影前 → 后 |
| --- | --- | ---: |
| 第 5 → 6 步 | 第 1、2 步 | 130,775 → 115,306 |
| 第 6 → 7 步 | 第 3 步 | 137,119 → 136,966 |
| 第 7 → 8 步 | 第 4 步 | 141,947 → 141,323 |
| 第 8 → 9 步 | 第 5 步 | 144,014 → 65,978 |

第 5 步包含一次较大的 `apply_patch`。其参数有 37,440 字符。该步 Provider 输出为 77,152 Token，其中推理 Token 为 45,096。前三次压缩都没有处理这一步。第四次纳入它后，输入投影才明显下降。

这能解释本次前三次缩减很少的直接原因。它不能单独证明每一个投影增减都由该补丁产生，因为计数还包含摘要、Provider 校准和工具正文清理。

### 3. 系统限制摘要大小，但没有设置完整请求的压后目标

[`ContextCompactor`](../../runtime/eidos_runtime/context/compactor.py) 把摘要自身限制在最多约 4,096 参考 Token 和 24 KiB。这个限制没有覆盖完整请求中的系统提示、工具定义、近期消息、工具参数、思考回放和结果。

摘要通过来源与控制事实校验后，系统就提交 `context.compacted`，并增加 `compaction_count`。完整请求的重建计量发生在提交之后。系统没有把“完整投影已降到某个目标”作为这次压缩有效的验收条件。

本次 14 份已提交摘要中：

- 7 份提交后的输入投影仍超过 68,000。
- 5 次缩减不到 10%。其中一次仅从 137,119 降到 136,966，减少 153 Token。
- 9 次采用模型摘要。5 次因模型引句校验失败，采用规则摘要。

因此，“14 次成功”只能表示 14 份有效摘要已提交。这个计数不能表示 14 次都腾出了足够空间。此前回答需要补上这个区别。

### 4. 循环会再次处理仍然超预算的上下文

[`RuntimeEngine`](../../runtime/eidos_runtime/runtime/engine.py) 在压缩后重建上下文并重新进入判断。只要投影有所下降，且仍超过预算，系统就可能再次进入压缩分支。

本次还有 7 次尝试以 `no_compactable_history` 结束。这 7 次都不包含模型摘要调用。它们说明上一份摘要已经用完当时可处理的旧历史，但完整输入仍超过预算。

对于估算造成的压力，当前循环会允许同一上下文状态继续尝试模型请求。下一步新增 Item 后，上下文状态会变化。最近三步之外又释放少量旧历史，系统就能再次进入同类压缩。

```text
输入投影超过 68K
  → 压缩三步之前的一小段历史
  → 完整输入仍超过 68K
  → 再次压缩，发现没有候选
  → 估算压力分支允许继续请求
  → 新步骤释放少量旧候选
  → 再次超过 68K并压缩
```

这次 21 次尝试的触发原因全部为 `window_pressure`。固定的 65,536 软阈值不是这次 14 份摘要的直接触发原因。这个额外软阈值仍然是需要统一的第二套策略。

14 次模型辅助摘要及回退累计耗时约 158.5 秒。摘要请求的 Provider 用量合计为输入 75,518、输出 33,321 Token。这是摘要开销，不是当前上下文占用，也没有换算为货币费用。

## Codex 的公开机制

### 触发预算与执行边界

OpenAI 的[配置文档](https://learn.chatgpt.com/docs/config-file/config-reference) 提供 `model_auto_compact_token_limit`。未设置时，系统采用模型默认规则。默认统计范围是完整活动上下文，另外也支持统计压缩窗口前缀之后的增长。完整窗口仍有独立约束。

本轮核对的 [`ModelInfo::auto_compact_token_limit`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/protocol/src/openai_models.rs#L517-L540) 使用以下普通默认规则：

```text
自动阈值 = min(模型或配置给出的阈值, 上下文窗口 × 90%)
若没有单独阈值，则使用窗口 × 90%。
```

源码中的默认有效窗口比例是 95%。它提供另一层完整窗口保护。具体模型元数据、阈值统计范围、Token Budget 功能和可选异步压缩可以改变实际触发行为，所以不能把 90%当成所有 Codex 模式的唯一阈值。

[`context_window.rs`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/session/context_window.rs) 分别计算当前活动上下文、自动阈值和完整窗口。这个通用计算没有用“窗口减去模型最大输出”代替自动阈值。

[`turn.rs`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/session/turn.rs#L592-L715) 在模型及其工具结束后检查用量。在需要继续执行且达到阈值时，系统压缩后继续。源码另有新 Turn 采样前、模型切换和可配置的 Turn 结束后处理。可选异步压缩还可以提前准备候选，但它受功能开关和 Provider 能力限制。

### 压缩作用于新的活动窗口

Codex 根据 Provider 声明选择远端 V2 压缩或普通模型摘要。OpenAI 的[独立压缩接口文档](https://developers.openai.com/api/docs/guides/compaction#standalone-compact-endpoint) 说明，接口接收完整上下文，返回包含压缩项及必要保留项的新窗口。后续请求使用返回窗口。压缩项可以是不可直接阅读的加密内容。

普通模型摘要路径也会重新组装活动历史，并重新计量。它保留有预算的用户消息和摘要，重新加入必要的当前环境。它不是 Eidos 这次采用的“固定留下最近三步，再逐步摘要更早历史”的处理方式。见 [`compact.rs`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/compact.rs#L391-L438)。

远端异步候选包含截止点。系统验证候选前缀后合并后续新内容。若安装候选后仍超预算，系统可以再做一次前台压缩。这个补救是有界的。见 [`compact_remote_v2_installation.rs`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/compact_remote_v2_installation.rs#L17-L69)。这不能外推为 Codex 对所有无缩减结果都有通用的拒收保证。

### 计量与局限

[`ContextManager::get_total_token_usage`](https://github.com/openai/codex/blob/8c076942cb70fba8e5c4732c23f1faabc4aed484/codex-rs/core/src/context_manager/history.rs#L924-L955) 使用最近请求的服务端用量，再补入该请求之后新增项的估算。它不把会话累计消费直接当作活动上下文大小。

公开文档和以上路径没有保证“每次都从 80%压到 20%”。Codex 的实现也包含“压缩后应明显低于阈值”的假设。Eidos 可以借鉴它的预算分离、活动窗口重建和状态校验，但不能据此宣称固定压缩率已经得到证明。

## Eidos 建议方案

以下内容是设计建议，本轮没有实现。

### 1. 分开模型能力上限与本次输出预算

系统应分别保存模型允许的最大输出和本次请求真实允许的输出预算 R。普通工具轮可以采用较小的默认预算，例如 8K–16K。用户要求大输出时，系统可以扩大 R，并同步提前压缩。

系统必须把 R 同时用于实际模型请求和上下文预算。系统不能只少预留输出，却继续请求 128K。用户已明确设置的真实请求预算也不能被静默改小。

系统保留以下硬约束：

```text
预计输入 + 本次真实最大输出 + 安全余量 ≤ 上下文上限
```

### 2. 给完整投影配置两个目标

系统应统一软阈值与窗口压力策略，并设置触发位置 H 和压后目标 L。它们分别控制何时压缩和一次压缩要腾出多少空间。

示例起点如下。这个例子不是 Codex 的承诺，也不是已经实现的 Eidos 默认值。

```text
W = 200,000，R = 16,000，M = 4,000
可用输入硬预算 B = 180,000
触发位置 H = min(W × 80%, B) = 160,000
压后目标 L ≈ W × 20% = 40,000
```

系统应同时计入固定提示词、工具定义、当前用户目标、摘要和近期完整交互。若这些必须保留的内容已超过 L，系统应记录目标不可达及其原因，并采用可达到的预算。系统不能为追求比例删除用户约束或拆坏工具调用、结果和思考回放的组合。

如果本次真实请求仍允许输出 128K，B 仍只有 68K。此时系统不能把 160K当作安全输入阈值。产品必须明确展示这个关系。

### 3. 按 Token 选择保留范围，一次重建窗口

窗口压力下，系统应从同一冻结来源选择一段完整历史，构建新的候选投影。系统应按 Token 为近期完整响应分配空间，替换固定三步保护。一个很大的最近响应需要有明确处理方式，不能永远被排除。

系统继续先清理可以回读的旧工具正文。对于已经落盘的大补丁和长参数，摘要应保留路径、版本、来源、变更和验证状态，避免它们长时间完整重发。系统继续保留原始 SQLite 事实。

系统应在提交前评估完整候选投影，检查目标与关键事实。模型辅助摘要继续复用当前 Structured Output 和确定性校验，不要求所有自定义 Provider 支持 OpenAI 的原生压缩接口。

### 4. 明确有效、部分有效与没有进展

系统应分别记录“摘要已提交”和“目标已达到”。如果候选仅减少极少 Token，系统不能把它当成一次已经充分释放空间的压缩。

如果一次候选未达到目标，系统可以在同一处理阶段扩大历史范围，再做一次有界补救。系统应通过来源集合、可回收 Token 和候选版本判断是否需要重试。同一来源没有变化时，系统应提前跳过无效调用。系统不需要限制整个 Run 的压缩总次数，也不需要用固定等待时间代替预算判断。

候选无法达到理想目标但仍在安全预算内时，系统可以保留事实并继续。真正无法容纳下一次请求时，系统需要使用明确的恢复或停止结果。系统不能靠重复的小摘要隐藏预算不足。

### 验收重点

1. 团队用本次 Run 的只读历史回放预算与候选选择。团队分别统计压缩次数、未达目标次数、无候选重试、耗时和 Provider 开销。团队不能预先承诺 14 次会减少到某个具体次数。
2. 测试覆盖 100K、200K及大窗口，覆盖较大输出上限、单次大补丁、长工具结果和高固定提示词占用。
3. 测试验证压后完整投影的目标，不只检查摘要不超过 4K。测试继续检查来源、纠正、未验证状态、取消、迟到结果和重启。
4. UI 继续以当前活动投影展示总量。UI 还应让用户看见触发位置、输出预留和压后是否达到目标。新投影在取得 Provider 用量前明确标为估算。

本轮发现需要先修正的是预算职责、固定三步保护、完整投影目标和无进展处理。仅调整百分比、换摘要模型或增加摘要调用次数，都不足以解决这次记录中的循环。
