不同 Session 可以并行

同 Session 的 Run 保持 FIFO。每个父 Run 最多同时运行 8 个子 Agent。Runtime 没有跨 Session 的 Run 总量配额。

三个入口共用 Run

Desktop 输入、渠道消息和定时触发都通过 RunApplication 接纳任务。渠道与定时调度在 Runtime 内运行。

运行事实与辅助资料分开保存

state.sqlite 保存执行状态。仓库索引可以重建。模型配置、凭据与大正文使用各自的受控文件存储。

一次 Run 如何推进

这张图展示正常执行的主要分支。Runtime 在各个安全点处理取消、用户输入、审批与子任务等待。

Desktop 输入 / 渠道消息 / 定时触发→ RunApplication.start → 同一套持久执行链路
  1. 01 / 接纳

    Runtime 创建并提交 Run

    Runtime 核对 Session、模型、输入和权限模式，并持久保存本次执行来源与快照。

    application/runs.py
  2. 02 / 调度

    Supervisor 启动 Worker

    同 Session 按 FIFO 执行。Supervisor 为 Run 持有线程、模型租约与取消资源。

    runtime/supervisor.py
  3. 03 / 构建

    Engine 准备当前 Step

    Builder 组合规则、历史、工具、记忆与可用仓库证据，并绑定上下文快照。

    engine.py · context/builder.py
  4. 04 / 采样

    Sampling 请求模型

    Runtime 保存 ModelAttempt，处理流式文本、ToolCall、思考回放与实际 Usage。

    sampling.py · model/gateway.py
↓ Engine 根据模型结果、待处理输入与运行事实选择分支

模型请求工具 → Runtime 执行工具

ToolDispatcher 校验调用与工具可用性。ToolCallRuntime 选择 Handler，Controller 管理实际执行边界。

校验参数→准备与 Diff→判定权限→提交 Intent→执行→核验→提交结果

实际副作用发生前，Controller 提交 Durable Intent。无需修改文件的操作可以返回 no_changes。权限阶段是否需要审批取决于模式和已授权范围。

↰ ToolResult + Event / Outbox 提交后，Engine 回到步骤 03，构建下一次模型请求。

模型无需继续 → Runtime 检查完成条件

Engine 处理尚未消费的输入、必要子任务和 Stop / SubagentStop Hook。Hook 要求继续时，Engine 返回模型循环。

满足完成条件后，Runtime 提交终态并投递通知。普通完成使用已有模型回答。

RunFinalizer 为需要提前收尾的路径生成有界、无工具回答；它不负责每一次普通完成。

并行范围：Dispatcher 只把连续且满足 parallel_safe 的只读调用分组并行，并按模型声明顺序汇总结果。

副作用顺序：每个 Run 只串行自己的提交 / 启动窗口。活动 Shell 不会持续持有这个门，其他 Run 也不共享这个门。

Hook 位置：UserPromptSubmit 位于采样前，PreToolUse 位于准备与审批前，PostToolUse 位于结果提交后。

源码：RuntimeEngine · ToolDispatcher · ToolExecutionController · HookService

Session 组织对话与工作空间

一个 Session 可以包含多个 Run。Session 持有 Local 或 Worktree 执行位置；Projectless 会话也有独立工作空间。

Run 组织一次任务执行

Run 固定模型与权限模式。Step、ModelAttempt、ToolCall 和 Durable Intent 保存更细的执行证据。

子 Agent 仍使用普通 Run

协作记录关联父 Run 与子 Session。每个子任务使用自身的执行、上下文与取消资源。

权限决定能做什么，恢复保留已经发生的事实

模型输出只提出调用。Runtime 根据当前 Run 的固定权限模式，决定审批、沙盒与实际执行。

查看不同权限模式的执行路径
所有模式都保留：参数校验、文件身份与版本检查、实际副作用前的 Durable Intent、取消、结果核验和未知结果记录。模型、项目文本与工具参数不能切换 Run 模式。本页控件只解释源码行为，不修改 Eidos 设置。

Runtime 如何执行权限

PermissionPolicyEvaluator 判定范围

普通工作空间操作使用已有权限。额外路径、网络与无沙盒执行进入相应的授权流程。

Seatbelt 与受控文件访问执行限制

manual / auto_review 默认使用既有保护。Shell 使用有效沙盒策略；文件执行器核对目录、FD、身份和版本。

高危人工批准可以放开具体限制

受保护路径和裸 Shell 无沙盒执行需要高危人工确认。自动审查不能代替这个确认。

Runtime 如何取消与恢复

取消先成为持久事实

Runtime 先写入取消状态，再通知 Worker、模型、工具进程和等待任务。迟到结果不能覆盖取消。

重启先核对未完成执行

Recovery 处理 Run、ToolCall、Approval、Intent 与 Outbox。满足条件的安全任务可以重新排队。

系统保留未知结果，并继续后续工作

Runtime 不猜测未知副作用，也不自动重放。未知记录本身不建立后续核验门，不阻止 Run 正常完成。

源码：PermissionPolicyEvaluator · ApprovalCoordinator · recover_runtime_facts · RunSupervisor

状态归属与实际代码目录

本视图区分执行事实、受控文件、可重建索引和内存资源。目录树只列出当前源码中存在的主要部分。

保存位置保存内容架构含义
state.sqliteSession / Run / Step / ModelAttempt / ToolCall / Approval / Intent / Event / Outbox，以及协作、计划、扩展和记忆元数据。Runtime 以已提交的执行状态为准。业务变化与对应事件在同一事务中保存。
受控文件与工作空间Workspace 文件、模型配置 models.json、独立凭据文件、Blob、记忆正文、插件包与快照产物。文件内容有各自的身份、权限与校验规则。API Key 不写入 SQLite 或普通事件。
repository.sqlite仓库 Inventory、Index、Symbol、Chunk、Map 与 FTS 检索资料。仓库库是可重建缓存。Watcher 只用于失效与索引更新，文件核验仍读取实际目标。
内存与诊断Worker 句柄、模型租约、CancelScope、活动 Shell、缓存与 Trace。这些对象服务于当前协调与诊断。它们不能替代持久执行事实。
事务与投递分开业务更新 + Event + Outbox 同事务提交→EventDelivery 投影并发送通知→Main 转发给 Renderer

布局还包含 thread_history.sqlite、logs.sqlite 和兼容用 memories.sqlite。新记忆的业务元数据由 state.sqlite 管理。各文件职责以 db/layout.py 和 MemoryService 为准。
