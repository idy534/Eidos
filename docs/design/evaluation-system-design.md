# Eidos 评测程序与执行方案

日期：2026-11-07。状态：设计方案，尚未实现统一评测程序，也没有执行本方案中的真实模型评测。

本方案的目标是回答三个问题：Eidos 能完成哪些真实任务？Eidos 在哪一步失败？一次产品改动是否带来了可重复的改善？

首期采用本地命令行程序、独立任务目录和离线报告。程序先支持 10 个校准任务，再扩展到约 40 个任务。程序不建设独立 Web 服务，不替代 Eidos 的 Agent Loop，也不把产品开发的 Full Suite 当成任务成功率。

本文中的任务配额、预算、目录、接口和命令均属于建议设计。本文用单独一节列出已经核对的现有入口。维护者不能把方案中的命令当成当前已经可执行的功能。

## 1. 评测范围与结果边界

评测程序需要维护三条结果线。

| 结果线 | 主要问题 | 首期处理 |
| --- | --- | --- |
| 本地真实任务 | 用户交给 Eidos 的工作能否完成？ | 程序通过生产 stdio 协议驱动 Runtime，外部程序检查答案和产物。 |
| 产品可靠性 | 取消、审批、重启、长任务和资源清理是否正确？ | 程序在可丢弃环境中执行有明确预期的场景。 |
| 公开原环境评测 | Eidos 在公开任务及其规定环境中表现如何？ | 后续接入。环境、预算和判分发生变化时，结果单独标为内部改编版。 |

Runtime 评测覆盖协议、应用服务、调度、模型、工具、权限和持久化。它不覆盖 Renderer、preload、Electron 生命周期和真实用户交互。程序需要另外保留少量 Desktop 验收案例。

首期报告按仓库理解、代码交付、终端工作流和产品可靠性分别报分。程序暂不把这四类结果合成为一个成熟度分数。

## 2. 当前可以复用的内容

以下事实依据当前分支的源码与文档核对。当前工作区存在其他开发改动。正式基线需要另外冻结受测构建。

| 当前入口 | 已有作用 | 评测程序的使用方式 |
| --- | --- | --- |
| `scripts/evaluate-request-content.py` | 在临时目录回放请求内容案例，使用模型包装器和启发式检查。 | 程序保留它作为专项回归，不把它当成通用开发任务评测器。 |
| `scripts/evaluate-context-compaction.py` | 检查合成历史的保留、继续执行、用量和延迟。 | 程序复用其案例思想，真实长任务另外验收最终产物。 |
| `scripts/evaluate-memory-learning.py` | 在受限工具范围内检查合成对话中的记忆选择和使用。 | 程序把它归入记忆专项，不据此推断完整产品完成率。 |
| `desktop/main/runtime-client.ts` | 启动 `python -u -m eidos_runtime`，校验协议并处理通知。 | Node 驱动器优先复用这个客户端及共享 DTO。 |
| `runtime/eidos_runtime/__main__.py` | 进入 `ResponseActionRuntimeServer`，沿用 RuntimeServer 的业务方法。 | 驱动器使用正常启动入口，不直接实例化 RuntimeEngine 作为正式成绩入口。 |
| `session/create`、`run/start`、`run/status`、`session/read`、`event/list`、`run/cancel` | 创建、观察和控制正常 Run。 | 驱动器通过这些协议完成一次尝试。 |
| `EIDOS_DATA_DIR`、`EIDOS_PROJECTLESS_ROOT` | 隔离 Runtime 数据与无项目工作空间。 | 每次尝试分别设置这两个目录；程序不复用日常数据。 |

目前没有在上述入口中确认一个可直接复用的统一任务包、外部判分、批量对照和报告程序。完整的 Model Attempt、Usage 和请求快照导出也需要在实现时逐字段核对。

## 3. 程序结构

```text
任务导入与校准
    ↓
冻结任务清单、受测构建、模型与预算
    ↓
创建独立工作区和 Eidos 数据目录
    ↓
驱动器 → 现有 RuntimeClient → stdio → Eidos 完整 Runtime
    ↓
收集公开协议事实、最终回答、产物和诊断记录
    ↓
停止受测进程、冻结产物副本
    ↓
外部测试 / 状态核验 / 问答评审 / 必要的人工复核
    ↓
分项成绩、失败分类、改动前后对照、优化清单
```

| 模块 | 职责 | 约束 |
| --- | --- | --- |
| Importer | 导入公开任务和历史需求，分离公开材料与私有判分材料。 | Importer 保留上游版本和本地调整说明，不让参考答案进入 Agent 工作区。 |
| Fixture Manager | 准备代码、依赖、初始状态和校准环境。 | 它只操作评测目录，不重置用户日常仓库。 |
| Runner | 执行批次、分配任务目录、检查预算和收集产物。 | 它只维护评测进度，不写 Eidos 业务状态。 |
| Eidos Adapter | 通过 RuntimeClient 提交任务、读取事件和取消 Run。 | 它不更换工具、不缩短模型循环，也不向模型补充隐含提示。 |
| Grader | 在外部环境检查最终结果。 | 它保留判分证据和自身版本，不信任 Agent 的完成声明。 |
| Analyzer | 根据已保存证据归类失败并计算对照结果。 | 它把已确认原因和待验证判断分开。 |
| Reporter | 输出 JSON、Markdown 和可离线打开的 HTML 报告。 | 报告展示样本、缺失数据和比较边界。 |

实现者优先使用 Node 标准能力、现有 RuntimeClient 和共享协议；Python 辅助程序使用标准库、Pydantic、pytest 和选定公开评测的官方工具。Parquet 读取和 Harbor 等评测依赖放在独立、锁版本的开发环境中，不进入 Eidos 发布包。实现者不为评测手写新的 Provider 协议、SSE 解析器或 Agent Loop。

首期批次按顺序执行。后续并行度由评测 Runner 控制。它只是本次实验的资源设置，不改变 Runtime 的跨 Session 并发策略。

## 4. 评测环境搭建

### 4.1 冻结构建与配置

维护者先创建一份独立、固定的受测构建。任务工作区不能与正在运行的 Eidos 源码目录重合。

每个批次记录以下信息：

- 程序记录 Eidos 构建标签、源码版本、是否含未提交变更，以及必要的源码副本或补丁。程序把工程版本标识保存在内部，不要求用户在报告中阅读长标识。
- 程序记录 macOS 版本、芯片、内存、语言、时区和工具链版本。
- 程序记录 Provider、精确模型标识、推理设置、上下文设置和模型配置快照。
- 程序记录权限模式、自动审查模型、联网条件、Shell 环境继承策略和可用工具。
- 程序记录 Skill、Plugin、MCP、Hooks、记忆、个性化和浏览器配置。
- 程序记录任务集、任务环境、判分器、评审配置、价格表和预算的版本。

基线批次使用全新的 Session 和数据目录。普通任务默认关闭记忆学习，并固定其余扩展配置；专项任务才启用被测功能。程序不能靠复用日常数据来获得模型凭据，也不能在报告中保存凭据。

`EIDOS_DATA_DIR` 不会独自隔离所有外部状态。实现者还需要固定 Projectless 路径、受管资源版本、浏览器配置、Electron user-data、临时目录、Shell 环境和任务依赖缓存。受管依赖可以复用已准备的固定版本，但程序需要记录冷启动与复用状态。Desktop 验收另设独立的 Electron user-data。

Provider 别名可能指向变化的模型。维护者需要记录运行日期和服务返回的版本信息。服务没有公开精确版本时，报告需要保留这个限制。

### 4.2 分开保存三类数据

建议使用以下逻辑布局。实际路径由机器配置决定。

```text
评测控制区：任务清单、私有参考答案、判分器、批次配置
Agent 工作区：每次尝试的初始代码、公开材料和输出
Eidos 数据区：每次尝试的 SQLite、Session、配置和日志
```

实现者需要把控制区与 Agent 的权限边界分开。仅把答案放在工作区外不能证明隔离有效。推荐使用独立评分用户或独立评分环境保存私有材料。Agent 使用专用 macOS 用户或虚拟机，且不连接日常项目和个人账户。

首轮可以由操作人员分别登录运行端与评分端，批量交接结果。后续驱动器再自动化这个过程。跨环境交接只传公开任务、产物和诊断记录；Eidos 的本地控制通道仍然使用 stdio。

正式评测前，维护者在私有区放入一个无业务价值的探针文件，并通过文件工具和 Shell 检查 Agent 无法读取它。程序还需确认公开代码快照不含后续修复、答案分支、可找到后续修复的 Git 对象与 reflog、隐藏测试和历史记忆。无法证明隔离时，该环境不能标为答案隔离通过。

### 4.3 选择运行环境

| 路线 | 用途 | 当前实施原则 |
| --- | --- | --- |
| macOS 原生 | 发现 Eidos 当前产品的优化点。 | 首期优先。任务使用能在 Mac 上稳定运行的代码和工具。 |
| 公开题的 macOS 改编版 | 借用公开题的任务思路和评分材料。 | 维护者记录每项调整，并重新校准答案与判分器。 |
| 公开题原环境 | 对照公开评测。 | 后续保留原始容器、资源、依赖、任务与评分方法。 |

SWE-Atlas-QnA-AA 提供了固定仓库、参考答案、评分条目和 Docker 镜像。Terminal-Bench 使用 Harbor；其完整任务集包含 GPU 任务。首期不能假设全部题目可以在普通 Mac 上直接运行。[SWE-Atlas-QnA-AA](https://huggingface.co/datasets/ArtificialAnalysis/SWE-Atlas-QnA-AA)、[Terminal-Bench 运行要求](https://www.tbench.ai/run)

### 4.4 权限与用户输入

首期默认使用 `auto_review`，并明确记录审查模型及其费用。评测任务的原始请求需要说明必要的普通本地操作。程序不能替用户确认保留的高危操作，也不能自动填入完全访问确认来获取无人值守能力。

`full_access` 只进入单独批次，并沿用现有 Desktop 人工确认要求。它需要独立用户或虚拟机等外部隔离。程序不能把这种模式的成绩与默认权限成绩直接混合。

每个任务在运行前声明允许的用户回复。独立完成组只提供题目已有的固定信息，不临时提供修复方向。允许人工协助的组另行运行并报分。程序分别记录普通权限确认、高危人工确认、澄清输入和纠正模型，避免把它们都算成同一种干预。

### 4.5 预算与预检

本地小任务可以先采用 20 分钟 Agent 时间作为校准起点；中型与长任务另外设定预算。维护者需要根据参考解法和首轮校准调整预算，并在正式批次前冻结。公开原环境评测沿用其任务预算。

每个批次都需要显式配置任务数、重复次数、时间预算、最大模型调用次数、费用上限和磁盘限额。程序在执行前输出预计尝试次数。费用数据不完整时，程序不能保证精确按美元停止，需要同时保留调用次数与时间限制，并标记限制来源。

预检需要确认：

- Runner 能启动和关闭固定 Runtime，且能通过初始化与健康检查。
- 任务的初始代码、依赖与参考解法已经校准。
- 任务所需工具、模型配置与资源已经准备完成。
- 程序能够收集回答、产物、事件与最低必要的诊断信息。
- 程序能够取消 Run，并完成受管资源清理。
- 评分器和评审模型可用，且私有材料没有暴露给 Agent。

预检使用模拟模型只能证明运行和协议链路。报告不能据此生成能力基线。

## 5. 任务库建设

### 5.1 首批与扩展配额

首批 10 题建议包含 4 个真实代码修改、2 个仓库问答、2 个终端工作流和 2 个可靠性场景。首批用来校准流程，不承担全面成熟度判断。

后续约 40 题采用以下建议配额：

| 类别 | 数量 | 候选来源 | 主要验收 |
| --- | ---: | --- | --- |
| 仓库理解 | 10 | SWE-Atlas-QnA-AA 和真实代码分析需求。 | 答案要点、源码证据、必要的运行观察。 |
| 代码交付 | 10 | 多个项目中已解决的缺陷与已完成的小功能。 | 目标行为、相关回归、构建和明确的修改范围。 |
| 终端工作流 | 10 | 可迁移的 Terminal-Bench 候选与真实本地任务。 | 文件产物、命令结果、服务状态和资源清理。 |
| 产品可靠性 | 10 | Eidos 的真实问题与相应恢复场景。 | Run 状态、重复副作用、取消、审批恢复和任务结果。 |

这些任务目前没有完成逐题筛选。维护者不能为了凑满配额硬搬不适合 macOS 的题目。无法保留有效验收条件时，维护者需要换题，或把该题留在原环境评测中。

40 题中建议保留 10 题用于阶段验收，其余用于日常优化。相同缺陷的变体和同一修复链不能跨两组分配。被反复用于调试的保留题需要转入开发组，并由新的任务替换。

### 5.2 一道任务必须具备的材料

| 材料 | 要求 |
| --- | --- |
| 用户请求 | 维护者尽量保留原始措辞，不把修复步骤写进题目。 |
| 初始状态 | 维护者提供修复前的代码、依赖和必要数据。 |
| 参考结果 | 维护者提供已验证的修复或目标状态。它只用于证明任务有解。 |
| 硬性验收 | 测试或检查器直接检查用户要求的行为和限制。 |
| 诊断标签 | 维护者标注语言、任务类型、难度、预计涉及模块和环境要求。 |
| 运行协议 | 任务声明预算、权限、允许的用户回复和故障注入条件。 |
| 版本与来源 | 程序记录任务来源、改编说明、授权信息和判分版本。 |

维护者需要先检查未修改代码，再检查参考修复。缺陷题的未修改代码应因目标缺陷失败，而不是因缺少依赖、导入错误或无法启动而失败。参考修复需要通过目标验收和相关回归。

维护者还需要准备一个明显不完整的解法，确认判分器会拒绝它。存在多种合理实现时，维护者应检查至少一种替代实现，避免测试只接受参考补丁的内部写法。

问答题需要检查缺少关键要点的回答会失败。可靠性题需要检查没有实现目标恢复行为的环境会失败。每道题的关键环境与参考结果至少重复校准两次。

### 5.3 任务清单格式

程序采用严格、带版本的 JSON 模型。公开请求和私有判分材料分别存放。下面是格式示例，不是已加入题库的任务。

```json
{
  "schemaVersion": 1,
  "taskId": "native-shell-background-001",
  "taskVersion": "1",
  "kind": "code_change",
  "source": "project_history",
  "comparability": "native_internal",
  "split": "development",
  "promptFile": "public/prompt.md",
  "fixtureId": "shell-before-fix-v1",
  "environment": "macos_native",
  "approvalMode": "auto_review",
  "memoryMode": "off",
  "budget": { "agentSeconds": 1200, "maxModelCalls": 40 },
  "interactionPolicy": "fixed_inputs_only",

```

真实批次还需有独立的 `suite.json`、`agent.json` 和 `batch.json`，分别固定任务列表、产品配置和执行预算。程序在运行前生成完整的有效配置，避免默认值变化后无法解释成绩。

## 6. 一次尝试的完整流程

一次尝试对应一个 `trial_id`。程序不能把一次失败后的重新运行覆盖到原记录。

1. Runner 读取冻结配置，检查预算，并登记尝试。
2. Fixture Manager 创建独立工作区、数据目录和 Projectless 根目录。它不携带其他尝试的历史、学习记忆或检索缓存。
3. Fixture Manager 准备依赖和初始状态，并进行健康检查。程序单独记录准备耗时。
4. Eidos Adapter 通过现有 RuntimeClient 启动 Runtime，完成 `initialize`，再调用 `session/create`。
5. Adapter 调用 `run/start` 提交原始请求，并记录返回的 Session、Run 和操作标识。
6. Adapter 持续接收通知，并通过 `event/list` 补读遗漏事件。程序根据当前协议的序号范围做有界分页和去重。
7. Runner 观察任务预算、审批、用户输入、进程退出和任务状态。它只按预先声明的规则回复，不给 Agent 添加临时提示。需要验证运行中状态的任务，同时启动独立观察器，保存进程、接口、审批或副作用证据。
8. 任务结束后，Adapter 通过 `run/status` 和分页的 `session/read` 收集最终事实。Runner 保存回答、代码差异、新增文件、测试产物和必要的运行状态证据。
9. Adapter 请求正常关闭 Runtime。Runner 等待资源静止，再冻结工作区结果和数据快照。
10. Grader 在干净副本中执行外部验收。私有测试只在这个阶段进入评分环境。
11. Analyzer 生成分项判分与失败原因。Reporter 更新批次报告。
12. Runner 清理本次拥有的进程、浏览器配置、端口与临时目录，并记录清理结果。

程序不能直接调用 `store.create_run`、改写 SQLite 状态或通过 `RuntimeEngine` 的自定义模型包装器来生成正式产品成绩。专项实验可以使用这些机制，但需要单独标为组件实验。

运行中的服务、取消竞态和故障恢复不能只靠结束后的文件快照验收。观察器需要按持久事件或明确状态触发检查，并保存时间和证据来源。离线 Grader 再结合这些外部观察判分。观察器不能只重复记录 Agent 的自述，也不能把参考答案传入任务环境。

### 6.1 超时、崩溃与断点继续

评测时间预算属于实验条件。预算达到时，Adapter 先调用 `run/cancel`，并保留一段有界的清理时间。只有正常关闭失败时，Runner 才终止本次拥有的进程树，并保留未知结果。这个机制不改变生产 Runtime 的自动恢复规则。

Runner 中断后，批次继续功能只接续尚未启动的任务。对于已经启动但没有结束证据的尝试，程序先读取状态和收集产物。它不能自动重新执行可能已产生副作用的任务。需要新尝试时，程序分配新的编号并保留原记录。

恢复场景在同一次尝试中保留数据目录并重启 Runtime。普通任务在不同尝试之间重新创建数据目录。程序需要区分这两种情况。

## 7. 判分设计

### 7.1 程序分别保存三种判断

- `outcome_pass` 表示最终答案或产物满足任务目标。
- `control_pass` 表示 Run 生命周期、权限和资源行为满足该任务的明确要求。
- `delivery_pass` 表示前两项与完整性检查都通过，且没有接受任务规则之外的人工纠正。

取消场景可以把 `canceled` 作为正确状态。普通交付任务则检查正常完成与资源清理。程序不能为所有任务硬编码同一个成功终态。

Agent 修好了代码但 Runtime 崩溃时，报告可以显示产物通过、完整交付失败。Agent 正常结束但外部测试失败时，报告需要显示任务未通过。

### 7.2 不同任务的判分器

| 类型 | 必要判分 | 可补充诊断 |
| --- | --- | --- |
| 代码修改 | 独立副本中的目标测试、相关回归、必要的构建与范围约束。 | 人工或模型检查设计、可读性和是否做了无关修改。 |
| 终端工作流 | 外部检查文件内容、数据结果、服务接口和进程状态。 | 程序分析重复调用、失败修正和工具等待。 |
| 仓库问答 | 按冻结的条目逐项判定答案。 | 程序核对引用是否存在，以及声称的运行是否有相应工具证据。 |
| 浏览器或 UI | 程序检查实际页面状态、交互结果和必要截图。 | 人工检查视觉与交互质量；程序不以构建成功代替界面验收。 |
| 产品可靠性 | 程序检查受影响的状态、资源和副作用次数。 | 程序分析恢复耗时和上下文是否保留目标。 |

一般代码任务不要求固定的工具调用序列。任务确实要求读取授权、执行验证或使用某个环境时，判分器才检查对应步骤。

Agent 写入的测试可以作为产物，但不能替代外部测试。Grader 检查测试是否被删改，并使用评分环境拥有的版本执行验收。它不能以 Agent 输出中的“测试全部通过”作为实际结果。

### 7.3 模型评审

本地任务优先使用程序可验证的结果。模型评审负责开放式问答和必要的软性质量检查。

每条评审输出包含判断、理由和对应的回答或产物证据。评审器不执行回答中的指令，不接收产品品牌和历史得分作为判断依据。它对缺少证据或无法完成投票的条目保留未评分状态。

首批任务需要人工核对全部模型判分。后续批次至少复核新增失败、改动前后不一致项和评审存在分歧的项目，并抽查通过项。维护者用已知正确、缺少关键要点和有明显错误的样本校准评审器。

SWE-Atlas-QnA-AA 原规则要求每条标准多数投票通过，并要求所有标准满足。公开配置包含评审模型、五票规则、提示词和结构化输出。保持这些规则的结果与本地附加的轨迹核验分别保存。[公开数据和方法](https://huggingface.co/datasets/ArtificialAnalysis/SWE-Atlas-QnA-AA)、[评审配置](https://huggingface.co/datasets/ArtificialAnalysis/SWE-Atlas-QnA-AA/blob/main/rubric_evaluation_config.yaml)

### 7.4 完整性与答案隔离

Grader 检查测试文件与评分输出是否被操纵、Agent 是否读取参考解法，以及是否从外部获取题目答案。程序根据实际证据判定违规，不能仅凭访问了某个网站就判定作弊。

本地任务的硬性限制在运行前写清楚。完整性证据不足时，程序交给人工复核并保留未确认状态。扫描器没有发现问题，不等于程序已经证明所有访问都合法。

本地交付判分、公开题原始判分和额外审计结果分别保存。维护者不能增加自己的扣分规则后，仍把成绩标为原始公开评测分数。

## 8. 首批可靠性场景

以下 10 项是候选类别。维护者需要为每项补齐可复现任务、故障触发点和外部验收条件后，才能把它们加入正式任务集。

| 场景 | 主要验收事实 |
| --- | --- |
| 取消与迟到结果竞争 | Run 的取消状态不被迟到结果覆盖，受管进程按规则清理。 |
| 审批等待期间重启 | 待审批操作保持未执行，原审批与操作范围仍然匹配。 |
| 副作用后、结果提交前重启 | 系统保留真实或未知结果，不自动重复执行该操作。 |
| 模型流中断、限流和服务恢复 | Runtime 保持可取消，任务恢复后没有丢失目标或重复副作用。 |
| 文件被外部修改 | 系统发现版本冲突，模型可以修正路径或重新读取。 |
| 后台 Shell 生命周期 | 后台服务在 Run 内可用，Run 收尾后相应进程被清理。 |
| 长任务发生上下文压缩 | 最终产物仍满足原目标、用户决定和已经完成的验证要求。 |
| MCP 或浏览器进程退出 | 错误被反馈，后续恢复没有误用旧连接或旧标签身份。 |
| 子 Agent 等待时收到消息 | 父任务能处理新输入，最终汇总与实际子任务结果一致。 |
| 跨任务的记忆与资源隔离 | 普通独立任务不读取上一题的答案，专项记忆场景按授权使用记忆。 |

故障注入优先使用可控的测试服务、进程控制和已有持久事件作为触发条件。程序不按固定睡眠时间猜测故障窗口，也不往生产 Runtime 添加会改变正常行为的隐藏开关。

## 9. 数据、指标和统计

### 9.1 每次尝试的证据

```text
manifest.json              固定配置、版本和状态
protocol.jsonl             脱敏后的请求、响应和通知
runtime-stderr.jsonl       本地诊断
events.jsonl               持久事件导出
answer.md                  最终回答
artifacts/                 输出、新文件和必要截图
workspace.patch            代码差异
checks.json                每项检查的结果与证据位置
judge.jsonl                评审条目、投票和证据
observations.jsonl         运行期外部观察与故障注入记录
result.json                标准化结果
analysis.json              原因分类与已确认程度
```

程序需要保存新增、删除和未跟踪文件。仅保存普通 `git diff` 不够。

程序为文件数量、日志、截图和产物设置可配置的采集上限。达到上限时，程序记录缺失或截断情况，并保留能继续定位的证据索引。程序不能把截断后的记录标为完整轨迹。

程序优先通过公开协议收集事实。完整用量和内部快照若无法从协议获得，MVP 可以在受测进程退出后，使用 SQLite backup API 和版本明确的只读导出器补充。导出器不能写业务表，也不能直接复制仍在写入的 SQLite 主文件来代替一致快照。后续确有跨版本需求时，再单独设计严格的诊断导出协议。

日志需要脱敏。它不能保存 API Key、Authorization Header、完整环境变量或用户日常敏感文件。程序只记录实际可获得的模型输出，不以完整隐藏推理作为评测前提。

### 9.2 成绩与分母

| 状态 | 处理规则 |
| --- | --- |
| `pass` | 该次尝试满足已定义验收。 |
| `fail` | Agent 或受测产品已经运行，但没有完成验收，包括非预期崩溃和预算耗尽。 |
| `invalid_setup` | Agent 启动前已经证明任务环境或参考验收有问题。程序公开列出并修复，不把它算成 Agent 能力失败。 |
| `unscored` | 判分器故障或证据不足，暂时无法判断。程序列出数量与原因，不把它当成通过。 |
| `not_run` | 批次因预算或人工停止尚未执行。程序保留原始计划数量。 |

Provider 在 Agent 运行期间失败属于本次实际交付结果。报告可以分出服务失败原因，但不能静默删掉这些尝试来提高完成率。故障注入题则按其预期行为判分。

正式对照使用每题相同的重复次数，首期建议三次。程序先计算每题各次得分的平均值，再计算同类任务的平均值。程序同时报告任务数、尝试数、预定数、有效判分数和所有异常状态。

完整批次的计算方式是：每题通过率 = 该题通过次数 ÷ 该题尝试次数；某类任务通过率 = 该类各题通过率之和 ÷ 该类题目数。10 题各跑 3 次，仍然是 10 个任务、30 次尝试。程序分别对产物完成和独立交付计算这些指标。

没有未评分项的正式批次才报告完整的点估计。有未评分项时，报告同时给出已评分结果与把缺失项视为失败或成功的上下界，并标明它是未完成报告。

### 9.3 必报指标

| 指标 | 定义与用途 |
| --- | --- |
| 目标完成率 | 程序按任务等权汇总 `outcome_pass`。 |
| 独立交付率 | 程序按任务等权汇总 `delivery_pass`。 |
| 可靠性通过率 | 程序单独汇总可靠性场景。 |
| 错误完成声明率 | 外部验收失败但 Agent 明确宣布完成的尝试数，除以明确宣布完成的尝试数。程序同时报告原始计数。 |
| 用户纠正次数 | 程序区分纠正、澄清和权限确认。 |
| 耗时 | 程序分别记录环境准备、Agent 活跃、等待人工、评分和清理时间。 |
| 用量与费用 | 程序分别记录主模型、审批模型、标题、压缩、记忆及评分模型。 |
| 恢复与清理 | 程序记录恢复耗时、残留进程和重复副作用。 |
| 波动 | 程序展示每题三次结果，以及稳定通过、稳定失败和结果不稳定的任务。 |

程序报告耗时的中位数、P90 和超时次数。样本很少时，报告保留逐题结果，避免只展示聚合数字。

费用缺失时，程序保存 `null` 和覆盖率，不能填零。Credits 与美元分开保存；程序只在有公开换算或账单依据时转换。程序同时报告成功和失败尝试的总消耗，避免只展示成功样本的成本。

## 10. 基线与对照方式

参考修复用于校准任务。当前固定 Eidos 的真实结果构成产品基线。Codex 或 Claude Code 的结果属于外部对照，首期没有它们也可以发现 Eidos 的优化点。

维护者按以下顺序建立对照：

1. 维护者先固定 Eidos、一个主模型、任务与判分器，建立初始基线。
2. 维护者改动一个产品方向，并保持模型和其余配置不变，比较 Eidos 改动前后。
3. 维护者另开批次评估模型选择，保留相同 Eidos 构建。
4. 后续适配器再驱动其他完整产品，保留相同任务、预算和验收规则。

不同产品无法使用相同模型时，报告明确比较的是产品和模型的综合表现。报告也要标出工具、权限、网络和扩展方面无法对齐的条件。

程序随机或交错安排新旧构建的尝试顺序，降低服务波动和缓存带来的顺序影响。程序记录无法控制的服务缓存，不把未公开的缓存状态当成已固定条件。

对照报告列出“旧失败新通过”“旧通过新失败”“两边都失败”和“不稳定”四组任务。统计区间按任务分组估计，不能把同一题的三次尝试当成三个独立任务。40 题只能提供当前任务覆盖下的证据，不能证明所有用户任务的总体成功率。

## 11. 从评测结果形成优化方向

Analyzer 为每次失败记录：第一个已确认偏差、相关证据、最终影响、主要原因、次要原因、确认程度和建议的验证实验。

| 观察到的问题 | 优先检查 | 后续验证实验 |
| --- | --- | --- |
| Agent 长时间找不到相关代码 | 检索结果、排序、读取范围和上下文占用。 | 同模型比较检索改动前后，并检查最终完成率。 |
| Agent 找到了代码但理解错误 | 依赖追踪、运行观察和上下文投影。 | 固定工具与环境，分别比较模型和证据组织。 |
| Agent 反复调用失败工具 | 错误可见性、参数契约、输出分页和替代路径。 | 使用相同失败条件，检查是否能修正并交付。 |
| Agent 改动正确但验证不足 | 验收目标、命令结果和收尾判断。 | 加入外部失败条件，检查错误完成声明是否减少。 |
| Agent 压缩后忘记要求 | 压缩前后的目标、决定、验证结果和副作用事实。 | 重复同一长任务，比较保留内容与最终产物。 |
| Agent 因权限等待无法完成 | 实际操作、授权证据、审批理由和人工时间。 | 固定权限模式比较审批改动，另查越权行为。 |
| Runtime 重启后重复执行 | Durable Intent、结果提交、恢复与事件顺序。 | 在同一持久阶段注入中断，并核对外部副作用次数。 |
| 正确性相同但费用或耗时明显上升 | 重复检索、上下文长度、审批调用和无效等待。 | 在通过率不下降的条件下比较耗时与总费用。 |

程序不能仅凭一个失败就把原因归给模型或提示词。一次诊断性重跑可以提供帮助，但它必须另存为实验，不回填到原基线。

维护者优先处理数据、权限、重复副作用等严重问题，再处理高频交付阻断，最后处理在正确性保持时的费用和交互优化。每个优化事项应包含受影响任务、证据、预期收益、最小改动和对应回归。

## 12. 报告与命令设计

首期报告至少包含以下内容：

- 报告展示受测配置、计划范围、实际覆盖和环境差异。
- 报告展示四类任务的完成率、交付率、耗时和费用。
- 报告展示逐题矩阵，用户可以打开失败尝试的检查结果和工具时间线。
- 报告列出已确认问题、待验证原因和前三个优化建议。
- 对照报告展示新增通过与新增失败，并给出证据链接。
- 报告列出未运行、未评分、数据缺失和仍未覆盖的产品部分。

CLI 建议采用以下流程。下面的 `eidos-eval` 尚不存在；实现者需要先完成第 13 节的阶段一和阶段二。

```text
eidos-eval doctor --config machine.json
eidos-eval import --source <公开数据集或历史任务包> --revision <固定版本>
eidos-eval validate --suite seed-10.json
eidos-eval plan --suite seed-10.json --agent baseline.json --repeat 3 --budget budget.json
eidos-eval run --plan plans/baseline.json
eidos-eval grade --batch batches/baseline
eidos-eval analyze --batch batches/baseline
eidos-eval report --batch batches/baseline
eidos-eval compare --baseline batches/baseline --candidate batches/candidate
```

`doctor` 检查机器和驱动能力；`validate` 校准任务与判分器；`plan` 冻结配置并列出消耗上限；`run` 执行任务；`grade` 独立评分。`grade` 可以在不调用 Agent 的情况下重新执行，但新评分必须保留版本和旧结果。

程序支持继续批次时，只调度未启动任务。程序不提供“覆盖原失败结果”的重试入口。程序默认只保存本地报告，不自动上传聊天、源码或评测结果。

## 13. 实施阶段与验收

| 阶段 | 要完成的工作 | 交付物 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| 一：任务与环境校准 | 维护者选择首批 10 题，准备隔离环境、参考解法和外部验收。 | 任务卡、环境说明、校准结果和冻结规则。 | 每题初始状态、正确结果和错误结果都能被正确区分，私有材料隔离检查通过。 |
| 二：最小评测程序 | 实现者完成配置、RuntimeClient 驱动、预算、证据采集、确定性判分和基础报告。 | 可执行 CLI、批次与尝试格式、1 题完整运行记录。 | 一道真实任务通过生产 stdio 链路运行并完成外部判分；取消、中断和重新评分可验证。 |
| 三：首个基线 | 维护者用固定 Eidos 和主模型执行 10 题，每题三次，并核对判分。 | 30 次尝试、逐题证据、费用和前三项优化建议。 | 报告能解释每个失败，未评分项已处理或明确列为未完成；程序没有用重跑替换失败。 |
| 四：扩大与优化 | 维护者扩展到约 40 题，保留阶段验收题，并完成一轮单方向优化对照。 | 分项基线、改动前后报告、复现案例和优化清单。 | 结果能显示收益、退化与不稳定项；团队根据证据选择下一项优化。 |
| 五：产品与外部对照 | 实现者补充 Desktop 验收、其他产品适配器，并评估公开原环境接入。 | Desktop 证据、同题产品对照和公开环境接入结果。 | 各组具备明确可比条件；无法对齐的环境被单独标注。 |

第一版不要求评分仪表盘、云调度、多机器管理、完整 GPU 集群或自动替代人工判断。工期和费用需要在首批环境与单题运行完成后估算。

每次产品优化先运行直接受影响的评测任务。阶段性评估再运行约定的完整评测批次。这个流程不改变仓库“只有用户明确要求才运行 Full Suite”的开发规则，也不把评测批次与 `pnpm test` 混为同一个入口。

## 14. 后续接入公开原环境

首期原生评测可以直接开始建设。公开原环境接入需要单独完成执行环境适配。

Harbor 允许自定义 Agent 运行在任务环境内，也允许 Agent 在外部通过环境接口控制任务。Eidos 的 macOS Runtime 更适合先研究外部适配方式。[Harbor 自定义 Agent 接口](https://docs.harborframework.com/agents/custom-agents)

这个接口的存在不代表 Eidos 已经具备接入能力。适配器必须证明文件读取、写入、搜索、仓库索引、Shell、cwd 和路径身份都指向同一个任务环境。只把 Shell 改成 `docker exec`，同时让其他工具继续读写宿主机，会得到不可信结果。

实施者需要先用三类小任务验证读写一致、依赖执行和取消清理，再接入原题。涉及新的执行后端、权限和文件身份规则时，实施者需要另做架构设计与定向验证。评测适配器不能绕过现有核心语义来制造一个替代版 Eidos。

Harbor 可以负责公开任务的环境和判分，Eidos 继续负责模型循环、工具决策和自身持久状态。原始判分与产品附加检查分开保存。[Harbor 任务格式](https://docs.harborframework.com/tasks/overview)

AA 的当前综合指数还包含未公开的 FrontierCode。公开子集结果不能命名为完整 AA Coding Agent Index。AA 的任务平均和三次尝试规则可以作为统计参考，Eidos 内部任务仍然单独命名。[AA 方法说明](https://artificialanalysis.ai/zh/methodology/coding-agents-benchmarking)

## 15. 维护者的实际操作顺序

1. 维护者选定固定的 Eidos 构建和一个主模型，记录权限与扩展配置。
2. 维护者搭建运行区与评分区，并完成目录、凭据和答案隔离检查。
3. 维护者整理首批 10 张任务卡，不急于填满 40 题。
4. 维护者验证参考结果、未修改结果和不完整结果，修复无效判分。
5. 实现者完成最小 CLI 和一题真实端到端验证。程序在此之前不能被当作已可用。
6. 维护者生成正式执行计划，检查尝试数量和费用上限，再启动真实模型批次。
7. 维护者完成独立评分，核对全部首批模型判分，并阅读每个失败的第一处偏差。
8. 维护者选择一项证据最充分、影响较大的优化，冻结其余配置后实现。
9. 维护者按相同规则比较改动前后，保留新增失败和成本变化。
10. 维护者把已确认问题转成最小产品回归，再逐步扩大任务库。
